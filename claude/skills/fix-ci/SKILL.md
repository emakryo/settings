# Fix CI - CIチェック修正サイクル

GitHub PRのCIチェック（GitHub Actions等）が全て通るまで、失敗したチェックのログを分析し、コードを修正してコミット・プッシュを繰り返します。
最大5回のイテレーションで終了します。

## 引数

```
/fix-ci [PR番号]
```

- `[PR番号]`: 対象のPR番号（省略時は現在のブランチに紐づくPRを自動検出）

## 手順

### 0. 前提確認

#### PR番号の特定

引数でPR番号が指定されていない場合：

```bash
# 現在のブランチに紐づくPRを検索
gh pr view --json number,title,state,headRefName --jq '{number, title, state, headRefName}'
```

PRが見つからない場合はエラーを表示して終了してください。

#### ローカルブランチの確認

PRのブランチがローカルでチェックアウトされていることを確認してください：

```bash
CURRENT_BRANCH=$(git branch --show-current)
PR_BRANCH=$(gh pr view <PR番号> --json headRefName --jq '.headRefName')

if [ "$CURRENT_BRANCH" != "$PR_BRANCH" ]; then
  echo "WARNING: 現在のブランチ ($CURRENT_BRANCH) がPRのブランチ ($PR_BRANCH) と異なります"
fi
```

ブランチが異なる場合はユーザーに報告して確認を取ってください。

### 1. CI修正サイクル（最大5回）

以下のサイクルを**最大5回**繰り返します。カウンター変数 `iteration` を 1 から開始してください。
各イテレーションの開始時に「イテレーション N/5 を開始します」とユーザーに報告してください。

---

#### Step 1: 未プッシュのコミットをプッシュ

ローカルに未プッシュのコミットがある場合はプッシュします：

```bash
# 未プッシュのコミット確認
UNPUSHED=$(git log origin/$(git branch --show-current)..HEAD --oneline 2>/dev/null)
if [ -n "$UNPUSHED" ]; then
  git push
fi
```

#### Step 2: CIチェックの完了を待機

CIチェックが全て完了するまで待機します。
**`gh pr checks` コマンドの `--watch` オプションを使用してください。**

```bash
# CIチェックの完了を待機（最大20分）
gh pr checks <PR番号> --watch --fail-fast
```

**注意**: `--watch` は全チェックが完了するかfailするまでブロックします。タイムアウトは20分に設定してください。

#### Step 3: CIチェック結果の確認

```bash
# チェック結果を取得
gh pr checks <PR番号>
```

#### 判定 - 全てのチェックが成功したか？

全てのチェックが `pass` / `success` の場合、**CI成功**と判断してサイクルを終了します。

**成功した場合**: 即座にサイクルを終了し、成功レポートを表示します。

#### Step 4: 失敗したチェックのログ分析

失敗したチェックがある場合、ログを取得して原因を分析します：

```bash
# 失敗したチェックの一覧
gh pr checks <PR番号> --json name,state,detailsUrl --jq '.[] | select(.state == "FAILURE" or .state == "ERROR")'

# 失敗したチェックのログを取得（GitHub Actionsの場合）
# まずワークフローのrun IDを特定
gh run list --branch <ブランチ名> --limit 1 --json databaseId,status,conclusion --jq '.[0]'

# 失敗したジョブのログを取得
gh run view <run_id> --log-failed
```

**ログの分析ポイント**:
- コンパイルエラー / 型エラー
- テスト失敗（どのテストが失敗しているか）
- lint エラー
- ビルドエラー
- その他のエラー

#### Step 5: エラーの修正

分析結果に基づいてコードを修正します。

1. **エラー内容の要約**: 失敗原因をユーザーに簡潔に報告
2. **コードの修正**: エラーを修正する最小限の変更を行う
3. **ローカル検証**: 修正後、可能であればローカルで同じチェックを実行して検証する

```bash
# 型エラーの場合
cd webapp && npm run type-check

# テスト失敗の場合
cd webapp && npm run test -- --testPathPattern="<失敗したテストファイル>"

# lintエラーの場合
cd webapp && npm run fix
```

4. **コミット作成**:

```bash
git add <修正したファイル>
git commit -m "fix: CI failure - <簡潔なエラー説明> (attempt N/5)"
```

5. **次のイテレーションへ**: `iteration` をインクリメントして Step 1 に戻る

---

### 2. サイクル終了条件

以下のいずれかでサイクルを終了します：

| 条件 | メッセージ |
|------|-----------|
| CI全チェック成功 | `✅ CIチェックが全て成功しました（N回目のイテレーション）。` |
| 最大5回に到達 | `⚠️ 最大イテレーション回数（5回）に達しました。残りの失敗を確認してください。` |
| 修正不可能なエラー | `❌ 自動修正が困難なエラーです: [詳細]` |

### 3. 最終レポート

サイクル終了後、以下のサマリーをユーザーに報告してください：

```
## CI Fix Cycle 完了レポート

- **PR**: #<番号> <タイトル>
- **イテレーション回数**: N / 5
- **結果**: [成功 / 最大回数到達 / 修正不可能]
- **修正コミット一覧**:
  - `<hash>`: <コミットメッセージ>
  - ...
- **最終CIステータス**:
  - [チェック名]: ✅ / ❌
  - ...
```

## 注意事項

- 修正はCIエラーの解消に必要な最小限の変更に留めてください
- テストが失敗する修正はコミットしないでください。ローカルで検証してからコミットしてください
- CIログが大量の場合は、失敗箇所に焦点を当てて分析してください
- 同じエラーが2回連続で発生した場合は、別のアプローチを試みてください。同じ修正を繰り返さないでください
- セキュリティに関わるチェック（secret scanning等）の失敗は自動修正せず、ユーザーに報告してください
- `--fail-fast` を使うことで、1つでも失敗したら早期に修正サイクルに入れます
