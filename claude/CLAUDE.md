## Git Workflow & Worktree Policy

### 作業ディレクトリの決定ルール
タスクを開始する際、以下の優先順位で作業ディレクトリ（ワークツリー）を決定してください。

1. **ユーザーの明示的な指定**: ユーザーが特定のディレクトリ（ルートディレクトリや既存の `.worktrees/xxx` など）で作業するように指示した場合は、必ずそれに従ってください。
2. **デフォルトの動作**: 特段の指定がない場合、新しいタスクや機能実装のために、プロジェクト内 worktree を作成して作業してください。

### Worktree Strategy (In-Project Worktree)
Claude Code はカレントディレクトリ外のファイルでの自動編集ができないため、以下の手順でプロジェクト内に worktree を作成します。

ユーザーからベースブランチの指定がない場合は、デフォルトブランチの最新をリモートから取得してからそれを base に worktree を作成します。指定がある場合はその指定に従ってください。

```bash
# デフォルト: リモートのデフォルトブランチ最新から worktree を作成
git fetch origin <default-branch>
git worktree add .worktrees/<feature-name> -b <feature-name> origin/<default-branch>

# ユーザーが別のベースブランチを指定した場合はそれを使用
# git worktree add .worktrees/<feature-name> -b <feature-name> <base-branch>
```


## Test-Driven Development (TDD) の徹底

このマシンでの開発では、**Test-Driven Development (TDD)** を厳格に遵守してください。

### TDDの基本原則

**Red-Green-Refactor サイクル**を必ず守ること:

1. **🔴 Red (失敗するテストを書く)**
   - 新機能や変更を実装する前に、まずテストを書く
   - テストを実行して失敗することを確認する
   - テストが失敗しない場合、テストが正しく書けていない可能性がある

2. **🟢 Green (テストを通す最小限の実装)**
   - テストを通すために必要最小限のコードを書く
   - すべてのテストが通ることを確認する
   - この段階では、コードの美しさよりも動作することを優先

3. **♻️ Refactor (リファクタリング)**
   - テストが通る状態を保ちながら、コードを改善する
   - 重複を削除し、可読性を向上させる
   - テストを再実行して、リファクタリング後も正しく動作することを確認

### 実装時の具体的な手順

#### 機能追加・変更時

1. **要件を理解する**
   - 何を実装するのか明確にする
   - どのような入力に対して、どのような出力が期待されるかを定義する

2. **テストケースを設計する**
   - 正常系のテストケース
   - 異常系のテストケース（エラー処理）
   - エッジケース（境界値、空値など）

3. **テストを先に書く**
   - テストコードを実装する
   - まだ存在しない関数やクラスを呼び出すテストでもOK
   - テストを実行して、期待通り失敗することを確認（🔴 Red）

4. **最小限の実装**
   - テストを通すための最小限のコードを書く
   - テストを実行して、すべてのテストが通ることを確認（🟢 Green）

5. **リファクタリング**
   - コードの品質を向上させる
   - テストを実行して、リファクタリング後も正しく動作することを確認（♻️ Refactor）

#### バグ修正時

1. **バグを再現するテストを書く**
   - バグが発生する条件を特定する
   - その条件下でテストが失敗することを確認（🔴 Red）

2. **バグを修正する**
   - テストが通るようにコードを修正
   - テストを実行して、修正が正しいことを確認（🟢 Green）

3. **リファクタリング（必要に応じて）**
   - コードの改善が必要な場合は実施（♻️ Refactor）

### 絶対に守るべきルール

- ✅ **テストなしでコードを書かない**: 実装前に必ずテストを書く
- ✅ **テストの失敗を確認する**: テストを書いたら、まず実行して失敗することを確認
- ✅ **テストの成功を確認する**: 実装後、すべてのテストが通ることを確認
- ✅ **既存のテストを壊さない**: 新しい変更で既存のテストが失敗しないことを確認
- ✅ **高速なテスト実行**: ユニットテストは数秒以内に完了すること（統合テストは除く）

### テストの品質基準

- **独立性**: 各テストは他のテストに依存せず、単独で実行可能であること
- **再現性**: 何度実行しても同じ結果になること（ランダム性や時刻依存を避ける）
- **明確性**: テスト名から何をテストしているか分かること
- **網羅性**: 正常系・異常系・エッジケースをカバーすること

### プロジェクト固有のテストコマンド

プロジェクトのCLAUDE.mdに記載されているテストコマンドを参照し、適切なマーカーを使用してテストを実行すること。
